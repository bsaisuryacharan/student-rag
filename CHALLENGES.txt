CHALLENGES LOG
Problems found during development and the solutions we landed on.
Each entry: a short problem (about 2 lines) and a short solution (3-4 lines).
Problems and solutions are described generically, not tied to the one example that surfaced them.


==========================================================
OPEN CHALLENGES  (confirmed, not yet solved)
==========================================================

C-009  Citation points to the wrong source location
Problem: For a query that targets a specific page or section, the answer can be correct
while the top-ranked citation points to a different page, sending the user to the wrong source.
Solution: Pending. Keyword (sparse) search over-ranks a page when a query token happens to
repeat many times on that page for unrelated reasons. Candidate fix: detect the page/section
the query targets and filter retrieval to it, so the correct location is both searched and cited.


==========================================================
RESOLVED CHALLENGES
==========================================================

C-001  Text outside the main column was not extracted
Problem: Text positioned outside the normal reading flow (labels inside boxes or shapes,
sidebars, floating headers, table cells) was dropped during PDF extraction, so it could
never be retrieved.
Solution: The default flow-based extractor only reads the main text column. Replaced it with
a layout-aware extractor that collects every text block (including floating ones) plus tables,
then sorts them by position to preserve reading order.
Commit 268821e - app/parsing/parsers.py


C-002  Word-vs-numeral query mismatch
Problem: Users phrase numbers as words ("page two", "section one") but documents print them
as numerals; keyword search treats these as different tokens and misses the match.
Solution: Stamp every chunk with both the numeral and word form of its page label, and
instruct the generator to match the page/section label named in the query. Both phrasings
now retrieve the right content.
Commit b6e19b3 - app/chunking/chunker.py, app/generation/service.py


C-003  Content bled across page boundaries in the chunker
Problem: Content from one page leaked into a neighbouring page's chunk, so a query about one
page or section could return content that actually belongs to the adjacent one.
Solution: Chunk overlap was copying the tail of one page into the start of the next chunk.
Refactored chunking to process each page independently, so overlap never crosses a page
boundary and each chunk's content stays pure to its source page.
Commit b2f55f5 - app/chunking/chunker.py


C-004  Reprocess silently failed on a stale document id
Problem: Re-running the processing pipeline never changed the results, because the request
used a document id from an earlier session.
Solution: A document's id changes on every fresh upload, so an old id hits nothing (a silent
404) while queries still use the live document. Always fetch the current id from the list
endpoint before reprocessing. (Loud-error follow-up tracked as F-002.)


C-005  Duplicate upload blocked re-processing
Problem: Re-uploading a corrected document was rejected as a duplicate, and the only delete
option wiped every document at once.
Solution: Added a per-document delete endpoint (users delete their own, admins any) that also
removes that document's vectors, and documented the in-place reprocess path for fixes that
don't require a re-upload.
Commit 7ec48bc - app/api/ingestion.py, app/store/qdrant_store.py


C-006  Managed Redis (TLS) connection failures
Problem: The task worker could not connect to the managed Redis broker over TLS, hung at
startup, or rejected the result backend.
Solution: Set SSL options in code rather than as URL params (the URL parser handles them
inconsistently); use a single logical DB and skip the result backend where the tier is
limited; disable worker mingle/gossip to avoid a pub/sub-related startup hang.
Files: app/worker/celery_app.py, start_workers.sh


C-007  Documents could get stuck at an intermediate status
Problem: A slow or oversized document could sit in a mid-pipeline status indefinitely, with
no terminal success/failure state.
Solution: Added a soft time limit that raises a catchable timeout (used to mark the document
failed with a message) and a slightly longer hard limit as a force-kill backstop.
Files: app/worker/celery_app.py, app/worker/tasks.py


C-008  Wrong embedding model in config
Problem: Startup crashed because the configured embedding model was not supported by the
local embedding library.
Solution: The config named a remote/API model; the local embedder only supports local models.
Switched to a supported local model so embedding runs on CPU with no API dependency.
File: .env (not committed)


C-010  Editing part of a document forced a full re-index
Problem: Updating any part of a document re-parsed, re-chunked, and re-embedded every page,
so changing a single page of a large document did the work of the whole document.
Solution: Added incremental re-indexing. Each page's text is fingerprinted and chunk ids are
page-scoped, so a page's vectors can be replaced on their own. On re-upload the new file is
diffed page-by-page; only changed/added pages are re-embedded and removed pages are dropped,
while unchanged pages keep their vectors. Exposed as an update endpoint on the document.
Commit 43019ab - app/schemas.py, app/chunking/chunker.py, app/parsing/service.py,
app/store/qdrant_store.py, app/embedding/service.py, app/worker/tasks.py, app/api/ingestion.py


C-011  Embedding could not retry or resume after a mid-way failure
Problem: Embedding wrote everything in one shot with no retry and no checkpoint, so a transient
vector-store error or a crash lost all progress and a re-run re-embedded the whole document.
Solution: Embed in bounded batches, each retried with exponential backoff on transient errors.
Every stored vector is tagged with its embedding model and a text hash, so a re-run skips chunks
already present unchanged (resume) and re-embeds only new/changed ones; stale points are pruned.
Needs payload indexes on chunk_id and embedding_model, backfilled on existing collections.
Commit a038c48 - app/config.py, app/store/qdrant_store.py, app/embedding/service.py


C-012  Scanned-document parsing was slow and could hang the whole pipeline
Problem: A scanned document with no text layer sends every page through a vision OCR model.
The pages were processed one at a time, and a single OCR call had no timeout, so a many-page
document took minutes and one slow/hung call could stall the entire job indefinitely.
Solution: Give each OCR call a per-request timeout so a hung call fails fast instead of blocking
forever. Split parsing into a fast local text-extraction pass followed by OCR of all scanned
pages concurrently, bounded by a configurable semaphore to respect provider rate limits.
Files: app/parsing/parsers.py, app/parsing/vision.py, app/parsing/service.py, app/config.py

FUTURE PROBLEMS  (agreed worth solving, deferred)
==========================================================

F-002  Reprocess endpoints should fail loudly
Problem: The reprocess steps return a quiet not-found on an unknown id (see C-004), so it is
easy to reprocess nothing without noticing.
Plan: Surface a clear error or confirmation, possibly via a single reprocess endpoint that
validates the id first.


F-003  Production hardening
Problem: Several operational gaps remain before the system is production-ready.
Plan: multiple web workers; queue backpressure (reject when the queue is deep); per-user rate
limiting; a health endpoint exposing worker count and queue depth; retry-with-backoff on
transient external errors; later, GPU embedding and workers spread across machines.


F-004  Incremental re-index granularity is limited by page-number diffing
Problem: Incremental re-indexing diffs by page number, so an edit that reflows content
(inserting text pushes later content onto new pages) marks every page from the edit point
onward as changed, even though only a little new content was added. Single-page formats
(DOCX/TXT parse as one page) get no benefit at all — any edit re-embeds the whole document.
Correctness is unaffected; only efficiency. Edits before the change point are still saved.
Plan: content-based diffing (anchor on text windows/shingles instead of page numbers) so only
genuinely new/changed content re-indexes regardless of reflow; and finer segmentation for
single-page formats so they can be partially re-indexed too.
